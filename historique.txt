HISTORIQUE DE DISCUSSION - fly_in
==================================

1. La classe Connection dans models.py peut-elle poser probleme telle quelle ?
-------------------------------------------------------------------------------
A l'origine, Connection(Zone) n'appelait jamais super().__init__(), donc une
instance de Connection n'avait aucun des attributs initialises par Zone :
absc, ordinate, max, cost, drone_in, path_to_end, hubs_connected.

Ca ne cassait rien sur le moment car :
- le parser range hubs et connections dans deux structures separees
  (self.hubs vs self.connections) ; une Connection n'entre jamais dans
  self.hubs.
- Map.path_finder ne parcourt que self.hubs.values() et zone.hubs_connected,
  peuple uniquement avec de vraies Zone (jamais l'objet Connection).
- MapDisplay accede aux coordonnees via connect.zone1.absc / connect.zone2.absc,
  jamais connect.absc directement.

Mais c'etait fragile : les type hints (Drone.pos: Zone | Connection,
Drone.path: list[Zone | Connection]) indiquaient une intention future
d'utiliser Connection comme un noeud a part entiere, et mypy ne detecte pas
ce genre de probleme (il verifie que les attributs existent quelque part
dans la hierarchie, pas qu'ils sont reellement initialises a l'execution).

-> Depuis corrige par l'utilisateur : Connection appelle desormais
   super().__init__(name, absc, ordinate, capacity, color), avec absc/ordinate
   calcules comme le milieu des deux zones connectees, et Zone.max renomme en
   Zone.capacity.

2. Quelle fonction/methode pour passer un set en iterable ?
-------------------------------------------------------------------------------
Un set est deja iterable directement (for x in mon_set, min(), sum(), etc.).
- iter(mon_set) -> obtenir explicitement un iterateur.
- list(mon_set) -> conversion en liste (ordre arbitraire).
- sorted(mon_set) -> liste triee (ordre deterministe).

3. min(set()) plante-t-il ?
-------------------------------------------------------------------------------
Oui : min() sur un set vide leve ValueError: min() arg is an empty sequence.
Dans path_finder, ce n'est pas un probleme car l'appel est protege par
`while remaining:`. Pour un cas non protege, utiliser min(mon_set, default=...).

4. Faire une ligne courbe avec pygame
-------------------------------------------------------------------------------
pygame.gfxdraw.bezier(screen, [points_de_controle], nb_segments, couleur)
ou, sans gfxdraw, calculer les points d'une courbe de Bezier quadratique
soi-meme et les relier avec pygame.draw.lines().

5. Isoler dans une liste de Zone celle avec le path_to_end le plus petit
-------------------------------------------------------------------------------
min(ma_liste_de_zones, key=lambda z: z.path_to_end)
Attention : ValueError si la liste est vide (sauf default=...) ; en cas
d'egalite, min() renvoie le premier rencontre.

6. Definir absc/ordinate de Connection au milieu des deux zones, et passer
   les parametres en float plutot qu'int
-------------------------------------------------------------------------------
Approche validee, avec deux nuances :
- Seuls absc/ordinate doivent passer en float (le milieu de deux int peut
  etre non entier) ; max_drones/capacity restent des int (ce sont des
  quantites).
- Elargir le type hint de int a float ne casse rien ailleurs grace a la
  "numeric tower" (PEP 484) : un parametre float accepte aussi bien un int
  qu'un float, donc les appels existants du parser restent valides.
- Le milieu de deux zones est toujours compris dans leur bounding box,
  donc pas besoin de toucher min_x/max_x dans MapDisplay.
- Aucune version de pygame n'etant epinglee dans pyproject.toml, les
  fonctions pygame.draw.* recentes acceptent les floats directement.

7. Une liste en comprehension sans PriorityZone leve-t-elle une erreur ?
-------------------------------------------------------------------------------
Non : `[t for t in ... if isinstance(t, PriorityZone)]` renvoie simplement []
si rien ne correspond, et `if []:` est False (liste vide = falsy) donc le
bloc if est juste ignore. Pas d'erreur.

8. Trier une liste de Zone avec sorted() selon path_to_end
-------------------------------------------------------------------------------
sorted(ma_liste_de_zones, key=lambda z: z.path_to_end)
Contrairement a min(), sorted() ne plante pas sur une liste vide (renvoie []).

9. drones_launcher : choisir en priorite les PriorityZone, sinon la zone au
   plus petit path_to_end, pour faire avancer les drones
-------------------------------------------------------------------------------
Conception discutee et validee (voir plan complet dans
~/.claude/plans/est-ce-que-la-whimsical-feigenbaum.md) :

- Zone.capacity peut etre None (voir point 11) -> traiter comme "pas de
  limite".
- Les BlockedZone ne doivent jamais etre une cible valide, meme presentes
  dans hubs_connected (leur path_to_end reste toujours inf).
- Un drone deja arrive ne doit plus etre traite par drones_launcher : plutot
  qu'un test `if d.pos is self.map.end`, move_drone retire directement le
  drone de self.map.drones des qu'il atteint self.map.end (en plus de
  l'ajouter a arrived_drones). drones_launcher doit alors iterer sur une
  copie (`for d in list(self.map.drones):`) puisque move_drone modifie la
  liste pendant la boucle.
- Un voisin n'est une cible valide que s'il rapproche reellement le drone de
  la fin (voisin.path_to_end < d.pos.path_to_end) : sans cette regle, si la
  zone la plus proche est pleine, le repli sur "le voisin disponible avec le
  plus petit path_to_end" pourrait faire reculer le drone.
- create_drones_list doit incrementer self.start.drone_in a la creation de
  chaque drone (sinon le premier decrement dans move_drone rendrait
  drone_in negatif).

Fonctions concues :
  pick_target(candidates, current_cost) -> Zone | None
    filtre les candidats plus proches de la fin (path_to_end < current_cost),
    les trie par path_to_end croissant, renvoie le premier qui a de la place
    (capacity None ou drone_in < capacity), sinon None.

  drones_launcher() : pour chaque drone encore en transit, exclut les
    BlockedZone des voisins, essaie d'abord les PriorityZone voisines via
    pick_target, sinon tous les voisins ; si aucune cible valide, le drone
    attend ce tour-ci ; sinon appelle move_drone.

  move_drone(drone, goal) : decremente drone_in de l'ancienne position,
    empile l'ancienne position dans drone.path, met a jour drone.pos/
    drone.target, incremente drone_in de la nouvelle position et
    drone.moves ; si goal est self.map.end, retire le drone de
    self.map.drones et l'ajoute a self.map.arrived_drones.

Note incidente relevee (hors scope, non corrigee) : create_drones_list
utilise "D{i}" comme chaine litterale (sans prefixe f), donc tous les
drones portent aujourd'hui le meme id litteral "D{i}".

10. Pourquoi sorted() plutot que min() dans pick_target ?
-------------------------------------------------------------------------------
Pas seulement parce que min() plante sur une liste vide (bien que ce soit
vrai). La vraie raison : on a besoin de plusieurs candidats dans l'ordre,
pas seulement du minimum, pour pouvoir passer au candidat suivant si le
meilleur est deja plein (capacite atteinte). min() ne renvoie qu'un seul
element ; sorted() donne toute la liste ordonnee pour permettre ce repli
dans la boucle for.

11. Dans quel cas zone.capacity peut-elle etre None ?
-------------------------------------------------------------------------------
D'apres parser.py (add_hub) : max_drone vaut None uniquement quand le hub a
un bloc d'options [...] non vide (au moins color=... ou zone=... present)
mais sans max_drones=... dedans. Si le bloc d'options est absent, max_drone
garde sa valeur par defaut (1), pas None.
Jamais None pour StartZone/EndZone (recoivent toujours self.drones, un int)
ni pour Connection (capacity type int, jamais int | None).

12. La verification `if not neighbors: continue` est-elle encore necessaire
    apres l'ajout d'un controle en L41 du parser garantissant un chemin
    entre start et end ?
-------------------------------------------------------------------------------
Probleme d'ordre d'execution releve : self.start.path_to_end (verifie en
parser.py:41) n'est mis a jour que par Map.path_finder(), lequel ne tourne
que dans Map.__init__, appele uniquement par parser.map_builder() -
execute APRES check_file() dans main.py. Donc au moment du controle L41,
path_to_end vaut encore sa valeur par defaut (inf), quelle que soit la
carte : le controle ne fait pas encore ce qu'il est cense faire.

Une fois ce probleme d'ordre corrige (verification deplacee apres
path_finder()), le garde-fou `if not neighbors: continue` devient inutile,
pour deux raisons :
- pick_target ne plante deja pas sur une liste vide grace a sorted().
- Garantie mathematique via Dijkstra : si start.path_to_end est fini, toute
  zone avec un path_to_end fini et non nul a forcement au moins un voisin
  non bloque avec un path_to_end strictement plus petit (c'est le voisin
  qui l'a relaxee dans path_finder) ; une BlockedZone ne peut jamais etre ce
  "parent" car son path_to_end n'est jamais mis a jour. Comme un drone ne se
  deplace que vers un voisin strictement plus proche de la fin, il reste
  toujours dans le sous-graphe atteignable : neighbors (filtre des
  BlockedZone) ne sera donc jamais vide pour un drone encore en transit.
